# Settings-center/UI audit finding — 2026-08-26T20:02:41-06:00

Scope: read-only audit of detached QindaQt base `496e5135ee4f40359f8b871eec130f0b8b02a241`. No source/build/test/commit action was performed.

## Decision

Ship this outcome as three explicit boundaries:

1. An independently restartable, session-bus-activatable `qindaqt-settings-service` owns `org.qindaqt.Settings1`, the schema/migration/persistence model, revision order, and publication. Do **not** make it a third tokenized child of `qindaqt-session`: that supervisor currently owns exactly the notification host and shell and ends the session when either exits (`src/session_supervisor/include/qindaqt/session_supervisor/session_process_supervisor.h:27-28`, `src/session_supervisor/src/session_process_supervisor.cpp:129-148`). Settings1 has no notification-presenter or compositor-PID authority.
2. A separate ordinary Qt Quick application, `qindaqt-settings`, owns a stable `notifications` route (default route while it is the only page, and accepted by `--page notifications`). It depends only on the public asynchronous Settings1 client/view model. This matches the normative ordinary-client boundary (`docs/wiki/architecture/settings-service.md:52-58`) and the planned `src/apps` dependency direction (`docs/wiki/architecture/module-boundaries.md:43-44,92-93`); it must not link `src/shell`, the interruption policy, or notification presentation.
3. Shell composition owns a scoped Settings1-to-DND binding: authenticated committed settings update the existing injected `NotificationInterruptionPolicy`, and shell UI mutations submit Settings1 transactions. Privacy remains independently driven by the authenticated lock monitor and continues to outrank interruption (`docs/wiki/architecture/module-boundaries.md:68-80`).

Discoverability should be concrete now, not deferred to the unimplemented launcher applet: install `org.qindaqt.Settings.desktop` and add a keyboard-focusable **Notification settings…** route action to the existing notification center. The current launcher is manifest-only/implementation-unavailable (`docs/wiki/shell/applet-runtime.md:49-75`), so a desktop file by itself is not a discoverable path in today's production shell. A narrow shell-private route launcher may start `qindaqt-settings --page notifications`; QML must not gain an arbitrary process-launch capability. Do not add a settings applet, change the notification-center manifest, or add another global shortcut. The notification applet intentionally has no capabilities (`data/applets/notification-center.json:19-24`) and must retain its read-only DND indicator.

The existing notification-center moon button may remain as a quick toggle, but only after rewiring it to the same Settings1 transaction controller. Today it directly writes `presentation.doNotDisturbEnabled` (`src/shell/qml/NotificationCenter.qml:52-75`) and the presentation controller exposes an in-process writer (`src/services/notification_presentation_model/include/qindaqt/services/notification_presentation_model/notification_presentation_controller.h:41-43`, `src/services/notification_presentation_model/src/notification_presentation_controller.cpp:192-195`). Leaving that path writable would create a non-persistent bypass. Make presentation DND read-only to QML; give the center a narrow setting controller with committed value, availability, pending, error/conflict, and `requestSet(bool)`.

## Settings page state and accessibility contract

- **Loading/authenticating:** show the Notifications page immediately, disable the DND `Switch`, and show plain-text “Loading Do Not Disturb setting…” with an accessible status name.
- **Ready:** the switch's checked state is the last authenticated committed value. Use an explicit checkbox/switch role and checked state, accessible name “Do Not Disturb”, and a description that low/normal banners are hidden while critical banners still appear only when privacy permits. Space/Enter toggles; Tab/Backtab reaches the switch, route navigation, retry (when present), and close/back controls.
- **Saving:** show “Saving…” visibly and accessibly and disable repeat mutation until the result is known. Pending UI must not claim persistence.
- **Conflict:** refresh the authoritative snapshot/revision. If it already equals the requested value, settle as success; otherwise restore the current value, preserve focus, show an alert “Changed elsewhere; current value reloaded”, and require an explicit **Apply my choice** retry against the new revision. Never silently overwrite.
- **Timeout/transport loss/owner replacement:** mark any outstanding result uncertain, disable the switch, label the retained display as “Last confirmed: On/Off”, and rebaseline before enabling or replaying anything. Ignore old-owner replies. A retry action may request a refresh; do not automatically resubmit a timed-out write.
- **Validation/persistence failure:** leave the authoritative value and revision unchanged, show bounded plain-text error content with an alert role, and re-enable retry when the client is ready.
- The quick control in the notification center uses the same states and transaction semantics. The applet remains only a read-only indicator.

These conventions extend the existing structural QML practice: explicit accessible labels/descriptions and focus chains are already asserted for the DND control (`src/shell/qml/NotificationCenter.qml:63-75`, `tests/shell/qml/tst_notificationsurfaces.qml:116-180`). Offscreen assertions prove semantics only, not actual screen-reader/focus operation; the current wiki makes that distinction explicitly (`docs/wiki/shell/notification-presentation.md:197-203`).

## Shell failure policy

- Before the first authenticated Settings1 snapshot, retain the policy module's existing deterministic default `off` (`src/services/notification_presentation_policy/include/qindaqt/services/notification_presentation_policy/notification_interruption_policy.h:18-20,37`).
- After a committed value has been accepted, service/transport loss holds that last confirmed value in the shell process while the client reauthenticates. This avoids unexpectedly resuming interruptions and does not claim persistence state is current.
- Owner replacement fences pending callbacks/signals, holds the last confirmed value, then applies only the replacement owner's complete authoritative snapshot.
- Lock privacy is not a setting and must not be wired through this client. Unknown/locking/locked/failure still clears all projections and suppresses even critical notifications (`docs/wiki/shell/notification-presentation.md:85-112`). DND updates may be retained while locked but cannot open presentation.

The client should reuse the repository's established owner-bound pattern: watch owner changes, subscribe to the exact unique owner before exposing it, bind every asynchronous call to that owner, carry request tokens/revisions, time out, and ignore stale replies (`src/services/notification_presentation_client/src/qt_notification_presentation_transport.cpp:47-72,141-187,222-259`). No blocking D-Bus call belongs in either UI process.

## Likely path ownership

- `data/settings/schema-v2.json`, retained v1 input, and `src/settings/*`: dedicated boolean DND key (not `services.notifications`; see `docs/wiki/architecture/settings-service.md:60-73`), v1→v2 migration, validated model, and atomic store. The current codec rejects every version mismatch rather than migrating (`src/settings/src/settings_document.cpp:20-40`).
- `src/services/settings_protocol/`, `src/services/settings_service/`, `src/services/settings_client/`: bounded wire values/errors; service/model/persistence composition; exact-owner async client and transport. Keep protocol, service, and client separate.
- `src/apps/settings_center/` plus focused QML: normal application entrypoint, route parser/view model, Notifications page, status/conflict UI.
- `src/shell/runtime/` and `src/shell/qml/NotificationCenter.qml`: shell DND binding, narrow route launcher, persistent quick-toggle state. Do not expand `NotificationCenterAppletAccess` mutation authority; it is intentionally read-only (`src/shell/runtime/notificationcenterappletaccess.h:8-30`).
- install data: D-Bus activation service and application desktop entry; additive targets in `src/CMakeLists.txt`; staged-install assertions. `src/settings/CMakeLists.txt:3-46` currently installs only the static model and data, while `src/shell/CMakeLists.txt:64-142` installs only shell presentation.
- docs/ADR: settings service, notification presentation, architecture/module boundaries, testing harness, roadmap, TASK_LIST/HANDOFF. A new ADR should decide service activation/lifetime, owner lineage, loss policy, migration, UI/process boundary, and whether the existing ADR-0010 “notification center owns the writable control” language (`docs/wiki/adr/0010-inject-shell-notification-interruption-policy.md:44-52`) is superseded or reinterpreted as a Settings1-backed quick control.

## Acceptance test matrix

1. **Schema/model/store:** v1 valid user/profile documents migrate to v2 with DND default off; explicit on/off round trip; unknown/corrupt/unsupported versions reject without mutation; atomic write failure preserves the old file; semantic no-op preserves revision; stale transaction conflicts; persistence failure rolls back model and publication.
2. **Service/wire:** valid snapshot/read/commit/remove, malformed types/keys/revisions, no-op, conflict, rollback, directed change publication, ownership collision, startup with missing/corrupt data, and clean stop/restart using isolated XDG roots.
3. **Client/private D-Bus:** subscribe-before-snapshot, exact-owner signal/reply acceptance, timeout, disconnected bus, service disappearance/reappearance, owner replacement, stale old-owner replies, resync after an uncertain commit, and bounded normalized errors.
4. **Settings view model/QML:** route parsing/default/deep-link, loading/ready/saving/conflict/error/retry states, switch role/name/description/checked state, Space/Enter, complete Tab/Backtab chain, focus retention after conflict/error, plain-text bounded errors, and reopen showing the committed value under offscreen software rendering.
5. **Shell composition:** initial default then authenticated initialization; committed changes update policy immediately; service loss holds last confirmed value; replacement rebaseline; notification-center quick writes only through Settings1; applet stays read-only; DND behavior retains critical bypass/Active/Recent/no replay; every lock/privacy state still outranks both on/off and pending/error states.
6. **Process/restart:** settings app save/close/reopen; service restart while clients remain; shell process restart while service remains; both service and shell restarted from persisted disk; settings app open across service replacement. Use private D-Bus/offscreen harnesses and report that these are not live desktop interaction.
7. **Packaging/gates:** staged install contains both executables, schema/migration data, D-Bus service and desktop entry and runs only installed paths; focused Debug/Release, complete registries, production build, QML lint, source-shape, strict docs/link check, whitespace. Run any real nested compositor, shortcut, focus, or assistive-technology check separately and label it accurately.

## TASK_LIST clarifications needed

- `docs/TASK_LIST.md:29-31` says “independent service/shell restart tests”, but the production supervisor intentionally couples shell and notification-host lifetime (`docs/wiki/architecture/compositor-session.md:63-74`). Treat “shell restart” as an isolated process-harness proof for this outcome and leave the supervisor trust chain unchanged. If the product instead requires in-session automatic shell restart, that is a larger restart-policy change needing explicit acceptance and an ADR.
- The first-class route (`docs/TASK_LIST.md:26-28`) and the later “complete applet-based settings center” (`docs/TASK_LIST.md:48-53`) are compatible only if this outcome is explicitly scoped to one standalone production Notifications page plus concrete entry links, not a new settings applet or full settings catalog.
- The phrase “transactions prove … owner replacement, timeout, and transport loss” (`docs/TASK_LIST.md:29-31`) mixes layers. No-op/conflict/rollback/malformed-input are model/service transaction evidence; owner replacement/timeout/transport loss are async-client/transport evidence and should be reported separately.
- “Screen-reader semantics” can be structurally tested offscreen, but item 6's live-interaction disclaimer (`docs/TASK_LIST.md:32-35`) means that must not be reported as a real assistive-technology run. Also define whether “stale” at `docs/TASK_LIST.md:19-21` means stale schema documents, stale transaction revisions, or both; the matrix above covers both.
