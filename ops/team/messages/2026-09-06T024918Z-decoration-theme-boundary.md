# Decoration theme boundary audit — 2026-09-06T02:49:18Z

- `src/decorations/qindadecoration.cpp:153-163` hard-codes active/inactive title and caption colors. This is a real dark/light theme gap, but the decoration plugin is a KDecoration3/KWin process component, not a first-party Qt app: `docs/wiki/architecture/module-boundaries.md` limits `src/decorations` to KDecoration3 and Qt Gui, and `docs/wiki/architecture/hybrid-chrome.md` explicitly says the current plugin uses checked-in colors and live theme wiring belongs to Shell/customization theme integration.
- No local KDecoration3 client-palette API or existing appearance transport was found. `ApplicationAppearanceController` cannot be instantiated per decoration, and direct Settings/D-Bus access would violate the boundary and create one client per window.
- Concrete future boundary: have the compositor/session theme integration own one resolved, validated decoration palette (derived from the same confirmed theme, with explicit CLI lock/fallback), publish it through a compositor-owned authenticated appearance protocol or compositor-to-decoration property adapter, and have `QindaDecoration` consume only a validated value with built-in fallback. Keep resolution/persistence in shell/app-appearance; keep painting in decorations. Extend the compositor/KDecoration workflow test to verify light/dark title, caption, border and button contrast after live theme changes and decoration recreation. Until that protocol exists, the hard-coded colors are an explicit bounded gap documented by hybrid-chrome, not something to patch with a per-window Settings client.
