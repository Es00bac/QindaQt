# Decoration palette API correction — 2026-09-06T02:53:00Z

Correction to the prior audit: installed KDecoration3 does expose the relevant public boundary. `/usr/include/KDecoration3/kdecoration3/decoratedwindow.h` declares `Q_PROPERTY(QPalette palette READ palette NOTIFY paletteChanged)`, `palette()`, `color(QPalette::ColorGroup,QPalette::ColorRole)`, and `paletteChanged`.

Upstream KWin evidence (`upstream-kwin/src/decorations/decoratedwindow.cpp:75`, `src/window.cpp:886-973`) forwards `Window::paletteChanged` to the decoration. `Window::setColorScheme()` rebuilds its `DecorationPalette`; Wayland server-side decoration palette changes call `XdgToplevelWindow::updateColorScheme()`. Therefore the bounded implementation path is for `QindaDecoration` to derive title/caption/border colors from `window()->palette()`/`window()->color(...)` and repaint on `paletteChanged`, using validated role fallbacks. This avoids a Settings client or new authenticated protocol.

Caveat: this public palette reflects KWin's decoration palette, not automatically the QindaQt app's `QPalette`; Qt application `setPalette()` is not itself evidence that KWin receives the same palette. If exact Qinda theme colors are required, a later compositor/session integration must set the KWin decoration color scheme/palette through the existing KWin/server-decoration path. For the present dark/light contrast requirement, consuming the public palette is the minimal reviewable repair. Test the decoration plugin with light/dark palette values, active/inactive groups, `paletteChanged`, border contrast, and recreation.
