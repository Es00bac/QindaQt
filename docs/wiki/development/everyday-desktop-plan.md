## Completion means an outcome, not a module

For each advertised journey, record source commit, reviewed package identity,
installed version, environment and observed result separately. Required evidence
is an ordinary graphical path and its keyboard equivalent; relevant terminal
or agent parity; negative/failure recovery; and an installed check after the
appropriate unit/private integration gates. A test which sees a lock frame but
never a password field does not establish usable unlocking.

Use a clean test account and disposable data. Physical hardware tests are
scheduled sessions with a recovery route; do not lock or suspend a person's
active work merely to satisfy a checklist. Source/build work stays on qinda.
Portage owns all installed software and system configuration. Keep developer
commands in evidence/runbooks; the acceptance user never has to type one.

   green/blue presentation; ED-24 qualifies everyday app behavior. A bounded

Keep at most three implementation outcomes active initially: one Platform,
one First-party and one Shell/agent outcome, with independent review capacity
reserved. Hardware and privileged test fixtures remain serialized. This is
a WIP target, not a claim that processes are running or capacity is unlimited.

## USB acceptance contract

This is the first visible improvement after reliability. A person inserts a
drive, sees its readable name in File Manager, opens it, copies a folder, and
chooses Eject in that same place. The drive is mounted automatically only under
the selected policy; first-use mounting must also be available by one obvious
action. Cancelled prompts or disabled notifications must not make a present
drive undiscoverable. No executable or autorun content launches on insertion.

Use disposable FAT/exFAT/ext4 media first, then an encrypted device. Check
already-mounted storage, startup with media present, multiple volumes,
read-only filesystems, permission refusal, unsupported formats, duplicate
labels and removal during work. A busy device offers understandable choices
without killing processes or forcing removal by default. Eject waits for
pending jobs and authoritative unmount/power-off; only then says it is safe to
unplug. Formatting is a distinct, clearly destructive workflow, not a recovery
button for “cannot mount.” File chooser, desktop notification and File Manager
must agree about current device state.

## Agent assistance that understands the chosen work

Preserve the existing QindaTK agent SDK, `qinda-agent` CLI/MCP, Calc/Note
document providers, browser tooling, public window commands and consented
capture/input. This plan proposes a joined experience, not replacement APIs.
Before accepting a new cross-process contract, ED-17 must record an ADR with
ownership, compatibility, threat model and limits.

The first useful journey is: **“Use these selected files and this document to
help me with this task.”** The user can see which application/document is
shared and choose read or edit access. The agent receives stable identifiers,
current selection, available actions and document revision. It does not infer
the selected file from a pixel or silently target whatever became focused.

Proposed requirements:

- Separate window/app metadata, selected document content, edit operations,
  screen capture and remote input. Existing authorization persists for its
  stated scope; normal repeated actions do not create redundant consent prompts.
- Default to a bounded snapshot and revisioned events. Subscription ends on
  revoke, document close, provider replacement or loss of authenticated session
  authority. Lock/unknown state prevents protected content exposure.
- Reuse the owning app's typed actions, transactions, validation and undo.
  CLI and MCP are adapters over the same public contract. Action receipts must
  distinguish accepted, completed, failed, cancelled and uncertain outcomes.
- A visible access indicator and one place to review/revoke grants should
  explain what is shared in plain language. This requires coordination with
  existing QindaTK document grants and Portal permissions, not a second policy
  store that can disagree with them.
- Password fields, keyrings, authentication prompts and clipboard secrets are
  excluded. Terminal cwd/selected text/output require explicit terminal-owned
  exposure; no ambient shell transcript or process-environment harvest.
- Treat document/web/terminal content as untrusted input, not instructions
  granting additional authority. Test stale target, focus switch, provider
  restart, hidden window, lock, revoke and hostile document instructions.
- For third-party apps lacking semantic providers, label the available
  accessibility or screenshot fallback honestly. Never promise universal
  semantic understanding from a single working Calc provider.

## Model allocation and usage discipline

The earlier planning preference was **Sol 6.1 for most work and Opus over Astra**.
The subsequent implementation instruction explicitly selects **Astra for the hardest bits**;
that instruction governs current dispatch.
These are starting assignments to evaluate by **accepted outcome per unit of
usage**, not a promise that a model will always succeed. OpenAI recommends
lighter models/settings for bounded work and comparing the same tasks to find
the lightest setting meeting the quality bar.
[OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection).
Its subagent guidance distinguishes narrowly scoped Luna work from demanding
Sol work. [OpenAI subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Anthropic lists Sonnet 5.5, Opus 5.5 and Fable 5.1; Fable is the escalation
option for demanding work when higher-effort Opus still falls short.
[Anthropic model overview](https://platform.claude.com/docs/en/models/overview).

## Gates for a wider beta

Before claiming the core experience is ready, a new test user should complete:

1. Login, idle, unlock, sleep and resume without hard reboot or terminal rescue.
2. See battery state, unplug/replug safely and receive useful low-charge status.
3. Connect to supported Wi-Fi and recover from a wrong password.
4. Insert a drive, open it, copy/move, Trash/restore, eject and reconnect.
5. Open/edit/save a document, recover an unsaved supported document, read/search
   and print a PDF, and choose a default application.
6. Pair a supported headset, choose mic/output and complete a browser call with
   consented screen sharing and visible stop control.
7. Attach/detach a display, change scale and recover from an unconfirmed change.
8. Install/update/remove a supported application graphically and recover from
   one defined failure without editing system files.
9. Complete the same core navigation with keyboard and a supported screen reader.
10. Grant an agent chosen context, perform one bounded edit, inspect/undo it,
    revoke access and verify further reads/actions are denied.
11. Open a terminal in the chosen directory and use shell/SSH/TUI workflows
    without the desktop breaking argv, input, PTY lifetime or focus.
12. Find help and export a reviewed diagnostic bundle without exposing secrets.
13. Launch a supported Android app and a supported Windows app from Applications;
    recognize green/blue origin, resize/group them with native apps, open/save
    supported files, and close/relaunch without losing other apps or data.

Use a published supported device/application matrix and explicit exclusions;
do not turn a two-machine pass into a general hardware claim. Capture failures
and terminal rescues as bugs. Update owning wiki pages and installed receipts
with each accepted slice. Feature-ledger progress advances only from integrated
behavior and evidence; this audit and its assignments add none.
