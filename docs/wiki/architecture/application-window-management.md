# Application window management

An application can ask QindaQt to place its own newly created window in a
container tab or tile. The application owns its content and shortcuts; the
compositor owns authenticated placement. See [ADR-0298](../adr/0298-native-application-window-placement.md)
and the [window container invariants](window-containers.md).

## Public boundary

`src/application_window_management` owns the installed protocol, Qt client,
pure placement planner, and example. The compositor transport authenticates
surface resources and delegates to the existing atomic Hybrid coordinator.
Consumers never include compositor-private headers or inspect QML storage.

`qindaqt_window_manager_v1` is an optional Wayland global at version 1. Bind it
on the same connection as the source and new `wl_surface`, then call
`place(request_id, source, created, placement)`. The XML is installed under
`share/qindaqt/protocols/qindaqt-window-management-v1.xml`; the generated client
header is under `include/qindaqt/application_window_management`.

| Placement | Wire value | Resulting layout |
| --- | --- | --- |
| Tab | 0 | New active page immediately after the source page |
| TileRight | 1 | Right half of the source tile |
| TileDown | 2 | Bottom half of the source tile |
| TileLeft | 3 | Left half of the source tile |
| TileUp | 4 | Top half of the source tile |

A solo source becomes a container with both windows. A grouped source retains
other pages and tiles. Tile requests split the actual source leaf at a 0.5
ratio; normal client constraints still apply. Tab requests activate the new
page in the same candidate mutation. Container IDs are generated by the server.

## Admission and failure

Both surface resources must belong to the connection that bound the manager.
They must be distinct normal, managed windows; the created window must still be
independent. The source must be restored, visible, and not iconified, shaded,
minimized, or fullscreen. The created window also must be restored and normal.
The source or newly created window must be foreground both at submission and
commit. Session lock denies admission and invalidates pending requests.
Temporary member-focus presentation in any container denies V1 placement.

The new surface may map after submission; the compositor waits at most five
seconds. Closing either surface, destroying the manager, disconnecting, locking,
or cancelling abandons pending placement. A refusal never closes the window or
publishes a partial topology. Application fallback may keep the independent
window, report the reason, or offer retry. Cancellation cannot undo a placement
already committed before the cancellation reached the server.

One connection may bind four manager objects, the compositor accepts at most
256 objects total, and each manager holds at most eight pending requests. A
connection may submit 64 requests in each ten-second admission period, including
invalid requests; destroying and rebinding a manager does not reset that budget.
Request IDs must be nonzero and unique while pending. Violating that identity
contract is a protocol error. Binding above the object limit also raises a
protocol error. Other placement refusals produce one `result` event.

| Status | Wire value | Meaning |
| --- | --- | --- |
| Accepted | 0 | Complete topology and scene committed; container ID provided |
| Denied | 1 | Ownership, foreground, lock, or presentation policy refused |
| Invalid | 2 | Invalid surfaces, mode, or stale topology |
| Unavailable | 3 | Runtime or scene could not commit |
| Timeout | 4 | Mapping or client completion deadline expired |
| Cancelled | 5 | Pending request cancelled before commit |
| ResourceLimit | 6 | Object, pending, or rate limit reached |

Status messages are bounded explanatory text, never identifiers to parse.

## Qt application integration

Construct `WindowPlacementClient` on the GUI thread after `QGuiApplication`,
and destroy it before the application object. Borrowed `QWindow` objects must
use the same Qt Wayland connection; the client does not own them. `place()`
returns a nonzero pending request ID, or zero with an optional reason when no
request was submitted. `finished` reports asynchronous completion. Destroying a
borrowed window cancels its pending requests; completion releases its observers.
The client deadline is six seconds and discards late replies. Unsupported
platforms remain quiet and `available()` returns false.

```cmake
find_package(QindaQtApplicationWindowManagement 1 REQUIRED CONFIG)
target_link_libraries(browser PRIVATE QindaQt::ApplicationWindowClient)
```

```cpp
#include <qindaqt/application_window_management/client.h>
using namespace QindaQt::ApplicationWindowManagement;

// Retain one GUI-thread client for the application's lifetime.
WindowPlacementClient placement;
// In the application's Ctrl+T handler, create/show its own new window first.
// Keep the ordinary application fallback when available() is false.
auto request = placement.place(sourceWindow, newWindow, Placement::Tab);
// A distinct application shortcut can request Placement::TileRight.
```

`qindaqt-window-placement-example` demonstrates Ctrl+T for a container tab and
Ctrl+Shift+T for a tile. It creates independent Qt windows and submits their
native surfaces after showing them. On an unsupported desktop it keeps those
ordinary windows. Existing browsers need an explicit application integration to
change their Ctrl+T behavior; registering this protocol does not modify them.

The SDK also exports `QindaQt::ApplicationWindowProtocol` for native Wayland
clients that use the generated header. Ownership, threading, and status are
the same wire contract; no Qt dependency is needed to generate a client's own
bindings from the installed XML.

## Verification

The focused planner gate covers solo/grouped sources, all tile directions,
source-page insertion, active selection, round-trip invariants, stale/owned
windows, invalid modes, and failed scene rollback. The Qt fallback gate runs
with offscreen and fatal warnings. Native acceptance uses a private virtual
compositor and private bus, including the installed SDK consumer and actual
application-created surface adoption; never the user's desktop.


Native qualification passed on 1920×1080 at scale 1 and 1.5. Each private scene
completed 77 responses: solo tab, grouped right tile, already-grouped target
refusal, pending cancellation, unmapped deadline, background refusal, destroyed
target, and a 70-request burst reaching connection rate admission. Read-only
scene snapshots verify all three members share one container, the initial page
is minimized, the new page has two disjoint equal-height tiles, and the separate
foreground window stays active. The installed SDK external consumer also
compiles and runs with fatal warnings on offscreen.


The private fork runtime must expose its matching library and decoration plugin
roots through `LD_LIBRARY_PATH` and `QT_PLUGIN_PATH`. The runner preserves the
fork executable basename and uses private HOME/XDG/bus roots with host portal
activation disabled. It never reads owner passwords or drives the live desktop.
Session-lock denial follows the fork's lock state; these no-lockscreen virtual
scenes do not qualify physical lock/input/capture behavior.

The native driver retains a live post-completion snapshot while the probe
windows still exist; Qt surface teardown before process exit is not treated as
the result of a completed placement request. Both output rows require that
completion fence as well as the exact loaded plugin and actual scene geometry.

The shared [semantic command boundary](window-management-commands.md) extends
first-party input/voice management separately. It does not grant V1 clients
global authority or change same-client surface authentication.

The native placement scenario now verifies actual output scale and Qt client DPR in addition to scene membership, active page, tiled frames and unchanged unrelated foreground. The actual-150% row records 77 protocol results and 58 read-only snapshots; a scenario filename alone is not scale evidence.

## Placement before the first frame

Applications may submit a request before showing their new window. A managed
identity can exist before the compositor marks the window ready for painting;
the server waits for both identity and readiness within the same five-second
deadline. Destruction, cancellation and lock still retire the pending request.
An early request never bypasses the ordinary foreground or ownership checks.

The private native probe submits its initial tab request against an unshown
window, then shows it 500 milliseconds later. The same request must complete
with actual scene membership. Normal and actual-150% scenarios remain required;
this source change alone is not installed-session qualification.

The private SDK client retains fatal Qt warnings. The compositor fixture runs
without that global switch because its copied, non-capability executable emits
upstream's expected failure to acquire real-time priority. Its logs and actual
scene checks remain mandatory; this is not a production priority qualification.
The deadline is checked even when readiness arrives after a delayed event loop.

The production fork disables dumpability at startup. Ordinary fixture clients
do not read its protected process maps. The runner enables Qt plugin diagnostics
for the compositor and requires the successful `qt.core.library` load record
for the exact candidate plugin path; metadata discovery alone cannot pass.
The probe disables those diagnostics and retains fatal Qt warnings. This
provenance check requires no privilege or change to compositor hardening.

Managed-window notifications queue placement processing until the registry
publication has reached the Hybrid topology subscriber. A ready first frame
alone does not mean the independent-window topology is already published.
